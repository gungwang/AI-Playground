# Wan2.2 Integration Summary for Gungwang AI Playground

Date: 2026-04-20

## Summary

Today's work focused on adding Wan2.2 into Gungwang AI Playground as a usable local video preset without forcing incorrect large-model downloads.

The project started with a broader Wan2.2 preset design that attempted to expose multiple operating modes, including Image2Video, Text2Video, and Start2End. In practice, that design was not a good fit for the current preset system. It caused the application to request Wan2.2 14B model downloads even when the intended user flow only needed the lighter TI2V-5B image-to-video path.

The final result was a simplified and stable Wan2.2 preset that ships as a TI2V-5B-only Image2Video workflow. This avoids unnecessary 14B downloads, matches realistic hardware constraints better, and aligns with the current Gungwang use case.

## Technical Details

### Code and asset areas involved

- `AI-Playground/modes/base/presets/Wan2.2.json`
- `AI-Playground/build/electron/win-unpacked/resources/modes/base/presets/Wan2.2.json`
- `AI-Playground/WebUI/src/assets/js/store/presets.ts`
- `AI-Playground/WebUI/src/assets/js/store/presetSwitching.ts`
- `AI-Playground/README_GUNGWANG.md`
- `AI-Playground/README_GUNGWANG.zh.md`

### Final Wan2.2 preset shape

The final source preset is a ComfyUI-backed `create-videos` preset named `Wan2.2` with a single Image2Video workflow.

Key characteristics:

- Backend: `comfyui`
- Category: `create-videos`
- Workflow type: TI2V-5B Image2Video only
- Recommended usage: discrete GPU / high vRAM systems

The required model set was reduced to the minimum practical Wan2.2 path:

- `Comfy-Org/Wan_2.2_ComfyUI_Repackaged/split_files/diffusion_models/wan2.2_ti2v_5B_fp16.safetensors`
- `Comfy-Org/Wan_2.1_ComfyUI_repackaged/split_files/text_encoders/umt5_xxl_fp8_e4m3fn_scaled.safetensors`
- `Comfy-Org/Wan_2.2_ComfyUI_Repackaged/split_files/vae/wan2.2_vae.safetensors`

The packaged preset copy under `build/electron/win-unpacked/resources/...` was kept in sync so testing against the unpacked build would not continue using stale behavior.

### Root cause of the failed 14B download behavior

The main issue was not ComfyUI itself. The failure came from how AI Playground preset variants are applied.

In `WebUI/src/assets/js/store/presets.ts`, variants are merged into the base preset through `applyVariant()` and `deepMerge()`. That means variant data is not isolated as a completely separate preset definition. Instead, overrides are layered into the base object.

This mattered because the earlier Wan2.2 design included additional variants for heavier 14B workflows. Once those variant overrides participated in the preset merge path, they affected fields such as:

- `requiredModels`
- `comfyUiApiWorkflow`
- mode-specific settings

As a result, the app could trigger model checks and download prompts for 14B assets even though the intended workflow for the user was only the TI2V-5B path.

### Runtime behavior and UX integration

Wan2.2 was also registered in `WebUI/src/assets/js/store/presetSwitching.ts` under the video VRAM warning set:

- `LTX-Video`
- `Wan2.1-VACE`
- `Wan2.2`

This keeps Wan2.2 aligned with the existing UX expectations for memory-heavy video presets.

## Solutions Implemented

### 1. Simplified the product decision

Instead of shipping multiple Wan2.2 operating modes in one preset, the feature was reduced to the one mode that is practical and intended for this environment:

- Keep `Wan2.2` as TI2V-5B Image2Video only
- Remove the 14B Text2Video and Start2End paths from the preset behavior

### 2. Fixed the problem at the preset level

The `Wan2.2.json` preset was rewritten back to a single-workflow design with no multi-mode variant structure driving 14B dependencies.

This ensured:

- no incorrect 14B required-model list
- no accidental 14B workflow activation
- no surprise download prompts for the wrong assets

### 3. Synced source and packaged assets

The same correction was applied to the unpacked packaged-copy preset so testing the packaged app and testing the source tree would behave the same way.

### 4. Preserved safety checks around resource usage

Wan2.2 remained in the high-VRAM video preset gating so users still get the expected warning behavior for heavy video generation tasks.

### 5. Updated project documentation direction

The intended documentation direction for Wan2.2 is now:

- Wan2.2 is supported
- the supported path is TI2V-5B Image2Video
- 14B variants are not part of the final supported preset behavior in this build

## Validation and Outcome

The work produced the following effective outcome:

- Wan2.2 is available as a built-in video preset in Gungwang AI Playground
- the preset uses the lighter TI2V-5B path only
- the app no longer needs to download Wan2.2 14B assets for the supported path
- source and packaged preset copies are aligned for testing
- Wan2.2 participates in the existing video-memory warning flow

From a product perspective, the feature moved from an overly broad design to a narrower but dependable implementation.

## What We Learned

### 1. Preset variants are not neutral feature toggles

In AI Playground, preset variants are deep-merged into the base preset. That makes them useful for small override sets, but risky for fundamentally different workflows with different required models.

For large behavioral differences such as TI2V-5B versus 14B video pipelines, variants can cause cross-contamination between model requirements and workflow payloads.

### 2. The practical target matters more than theoretical feature breadth

Wan2.2 14B support may exist at the model level, but that does not mean it should be exposed as a default built-in preset for this app.

For the current Gungwang AI Playground target environment, TI2V-5B is the practical default. It is lighter, more aligned with expected hardware, and less likely to fail during onboarding.

### 3. Packaged assets must be considered during debugging

Changing only the source preset is not enough when the user is testing an unpacked packaged build. If the copied preset under `build/electron/win-unpacked/resources/...` is stale, the app can appear unfixed even when the source tree is correct.

### 4. Product documentation must follow the shipped behavior

When a feature direction changes from multi-mode support to a single supported path, the README and release notes must be updated to reflect the final product decision. Otherwise, user expectations and actual runtime behavior drift apart.

### 5. Root-cause fixes are better than suppressing symptoms

The correct fix was not to hide a download prompt or special-case a single code path. The correct fix was to remove the underlying preset structure that made the app think the 14B models were part of the supported default experience.

## Final Status

Wan2.2 support is considered successfully integrated for the intended Gungwang use case as a TI2V-5B Image2Video preset.

The project outcome is not "full Wan2.2 mode coverage." The successful outcome is a stable, realistic, and supportable Wan2.2 integration that does the right thing by default.
